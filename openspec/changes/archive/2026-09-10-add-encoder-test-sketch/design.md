## Context

В `motor_controller.ino` уже есть рабочая энкодерная логика: квадратурный декодер (`QUAD_TABLE`), ISR `PCINT1_vect` на PORTC (A0-A3), дебаунс через `MIN_TICK_US`, расчёт скорости в `measureSpeed` с учётом `motorSign`.

Возникли проблемы с управлением ботом. Нужно изолировать и проверить чтение энкодеров: человек вручную крутит колёса, поворачивает их вперёд/назад и убеждается, что значения и направления корректны.

**Ключевое ограничение (обнаружено при реализации):** на ATmega328P (Nano) библиотека `SoftwareSerial` объявляет `ISR(PCINT0_vect)` и алиасит на него `PCINT1_vect` и `PCINT2_vect`. Поэтому использовать `ISR(PCINT1_vect)` для энкодеров одновременно с SoftwareSerial невозможно — конфликт `multiple definition of '__vector_4'` на этапе линковки (по этой же причине текущий `motor_controller.ino` не компилируется). Для тестового скетча выбираем Hardware Serial (D0/D1, USB) вместо SoftwareSerial/HC-06.

## Goals / Non-Goals

**Goals:**
- Отдельный скетч `encoder_test.ino`, изолирующий чтение энкодеров и вывод через Hardware Serial (USB)
- Показывать тики каждого колеса со знаком (плюс = бот едет вперёд) и скорость в мм/с
- Использовать уже проверенную энкодерную логику из `motor_controller.ino` без отклонений

**Non-Goals:**
- Не проверять драйвер моторов (L298N, ШИМ, направления питания)
- Не модифицировать `motor_controller.ino`
- Без PID, рампы, торможения — только чтение энкодеров
- Не использовать SoftwareSerial/HC-06 в тестовом скетче (конфликт с ISR PCINT1)

## Decisions

**1. Вынести энкодерную логику в тестовый скетч как есть.**
Решено скопировать прошивку декодера из `motor_controller.ino` (QUAD_TABLE, `updateEncoder`, дебаунс, ISR на `PCINT1_vect`, инициализация пинов и регистров PCICR/PCMSK1) без изменений. Это гарантирует, что мы тестируем именно тот код, что будет в боевом, а не его реплику с потенциальными расхождениями.
Альтернативы:
- Вынести энкодерную часть в общий модуль (`.h`/`.cpp`) для переиспользования — отклонено: меняет структуру боевого скетча, шире scope.
- Писать логику начисто — отклонено: риск расхождения с боевым поведением.

**2. Направление вывода = «вперёд» соответствует движению бота.**
Применяем `motorSign` к показываемым тикам (как делает `measureSpeed`): правое колесо по часовой, левое против — бот едет вперёд → показывается `+`. Так человек крутит колесо «вперёд» и видит плюс, «назад» — минус.

**3. Вывод через Hardware Serial (D0/D1), HC-06 подключён на D0/D1, раз в секунду, построчно.**
Используем встроенный `Serial` (Hardware UART) вместо SoftwareSerial — он не использует PCINT-вектора и не конфликтует с `ISR(PCINT1_vect)`. HC-06 подключается к D0 (RX) и D1 (TX) через делитель на TX→RX HC-06 (HC-06 RX не 5V-tolerant). Данные идут и в USB-монитор, и в HC-06 одновременно. При перепрошивке HC-06 нужно отключать (загрузчик использует D0/D1). Формат: строка вида `L:<ticks> R:<ticks> <L_speed_mm_s> <R_speed_mm_s>`, без ANSI/управления курсором.
Альтернативы:
- btSerial/SoftwareSerial на D12/D13 — отклонено: алиасит PCINT1_vect, конфликт линковки с ISR энкодеров (multiple definition of '__vector_4').
- Hardware Serial без HC-06 (только USB) — отклонено: пользователю нужны данные через HC-06.

**4. Скорость в мм/с считается локально.**
Переиспользуем формулу: `mmPerTick = PI * WHEEL_DIAMETER_MM / TICKS_PER_WHEEL_REV` и дельту тиков за окно. `WHEEL_DIAMETER_MM = 67`, `TICKS_PER_WHEEL_REV` из тех же констант, что в боевом скетче.

## Risks / Trade-offs

- **Копирование кода → рассинхрон с боевым скетчем.** Если энкодерную логику потом поправят в `motor_controller.ino`, тестовый скетч останется со старой. → Mitigation: документировать в шапке `encoder_test.ino`, что это копия с `motor_controller.ino` (нужно синхронизировать вручную). Скоуп нового change сводит это к минимуму.
- **НОЛИ при застое.** Если показать только при изменении — человек может подумать, что связь потеряна. → Mitigation: выводить раз в секунду всегда, даже если тики не меняются (как сейчас делает боевой скетч).
- **Тестовый скетч не проверяет путь через HC-06.** Он выводит через USB (Hardware Serial). → Mitigation: это осознанный выбор из-за конфликта SoftwareSerial/PCINT1; HC-06-путь в `motor_controller.ino` остаётся самым проблемным местом и требует отдельного решения (см. impact change `move-encoders-to-portc`).
