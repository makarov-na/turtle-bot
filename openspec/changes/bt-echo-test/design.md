## Context

`bt-keyboard-control` внедрил управление ботом через HC-06 (текстовый протокол `set_speed`), но проверка на железе
вскрыла нестабильность RFCOMM-линка: он падает раз в ~5 с при непрерывных записях ПК→бот, при чтении, и даже в
отсутствие трафика. Причём и раньше, когда бот слал `hello` раз в секунду (односторонний поток бот→ПК), соединение
выглядело стабильным минутами — возможно, обрывы маскировались мгновенным переподключением в сочетании с регулярным
трафиком.

Скетч-эхо намеренно выносится в отдельный change: это автономный «измерительный прибор» канала, который не должен
зависеть от состояния моторов, watchdog или протокола управления.

## Goals / Non-Goals

**Goals:**

- Отдельный скетч `bt_echo_test.ino`, который принимает строки с ПК через HC-06 (Hardware Serial D0/D1, 9600 бод) и
  возвращает их с нарастающим счётчиком.
- Консольная инструкция проверки на Linux, исключающая ложный результат из-за локального `termios ECHO`.
- Эмпирически проверить поведение линка при непрерывном **двунаправленном** трафике (пинги каждые 200 мс + ответы бота):
  доживёт ли поток ≥60 с или падение повторится на ~5 с.

**Non-Goals:**

- Изменение `motor_controller.ino` и протокола `set_speed` — они не трогаются.
- Поиск и устранение первопричины обрыва на уровне радио (btmon/sniff) — за пределами этого change; он лишь даёт
  воспроизводимые данные для решения.
- Отдельное GUI/приложение на ПК — только консольные команды и скрипты на stdlib.

## Decisions

### 1. Скетч повторяет строки с префиксом и счётчиком, а не «сырое» эхо

Ответ вида `echo <n>: <line>\n`. Прямое зеркало байтов не позволяет отличить переданный скетч от перекрёстной наводки и
не даёт метрики потерь. Счётчик делает пропуск пакета очевидным, префикс `echo` снимает двусмысленность с локальным эхом
терминала. Альтернатива «только `3: ping`» отклонена: префикс идентифицирует источник в логе.

### 2. Буферизация по строкам до `\n`, без блокирования `loop()`

Тот же паттерн, что в `bt-keyboard-control.processSerial`/`handleCommand` — меняем только формат ответа. Накопление в
буфер до `\n`, ответ после перевода строки. На 9600 бод строка ~30 байт вписывается легко.

### 3. Никакого watchdog и L298N

Тестированию нужен канал в чистом виде: бот отвечает на любую строку, даже если ПК молчал 10 с. Motor-логика и
стоп-таймеры остались бы причиной ложных «обрывов». Это намеренное отличие от `bt-keyboard-control`.

### 4. Приветствие однократно в `setup()`

Полезно для проверки, что линк жив в момент старта и что залит именно тестовый скетч (идентифицирующая строка
`echo test ready`). Периодических сообщений нет — иначе тест «падает ли без трафика» был бы невозможен.

### 5. Проверка только через консоль Linux, и обязательно `stty raw -echo`

RFCOMM-порт — tty, и локальный `termios ECHO` без `stty -echo` вернёт проверяющему его же строку без участия бота (
ложный положительный результат). Поэтому проверка начинается с `sudo rfcomm bind 0 <MAC> 1` и
`sudo stty -F /dev/rfcomm0 raw -echo`, затем тройной прогон:

```
L1  manual:    cat в фоне + echo "ping"           → видим “echo 1: ping”
L2  RTT-loop:  пинги 200мс, фиксация RTT и потерь
L3  stability: ≥60с непрерывно, момент первого разрыва
```

L2/L3 — маленький stdlib-скрипт Python (`os`/`select`), без игрушек.

## Risks / Trade-offs

- [Локальный termios echo даст ложные ответы] → инструкция жёстко требует `stty -F /dev/rfcomm0 raw -echo` перед тестом
  и объясняет, почему.
- [Линк падает и при двунаправленном трафике] → вывод: обрыв железный (модуль/питание), дальше — тест
  смартфоном-мастером и/или btmon; это ожидаемый исход эксперимента, данные равноценны.
- [Скетч могут спутать с боевым] → уникальная строка приветствия `echo test ready` и отдельная папка `bt_echo_test/`.
- [Проброс через USB-монитор одновременно с HC-06] → Hardware Serial один, канал общий; проверку вести по одному
  интерфейсу за раз, как указано в тестах.

## Migration Plan

1. Создать `src/motor_controller/bt_echo_test/bt_echo_test.ino` и залить в Nano ардуино-кли eherм вместо боевого.
2. Прогнать L1–L3 через консоль; записать результаты (в т.ч. момент первого обрыва).
3. По окончании вернуть боевой `motor_controller.ino`.
4. Откат: обратная заливка боевого скетча из git; тестовый скетч просто не используется.

- Нужно ли после обрыва автоматически перезапускать цикл в скрипте проверки, или каждое соединение стартует свежим
